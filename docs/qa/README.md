# Проверки на боевом сайте и рабочие инструменты

Копии скриптов, которыми проект проверялся на https://bidfolio.co.uk и вливался в `main`. Оригиналы жили в рабочей среде
(`/home/user/qa`, `/home/user/tools`), которая не сохраняется между сессиями; здесь они лежат, чтобы их можно было
восстановить. Секретов в них нет: ключи подставляет сеть среды (`proxy-injected` — заполнитель), адреса баз и данные
тестовых аккаунтов читаются из файлов вне репозитория.

## Что нужно, чтобы запустить

- Playwright с Chromium (в облачной среде: `/opt/node-tools/node_modules/playwright`); исходящий трафик идёт через
  `HTTPS_PROXY`, для `fetch` в Node — `NODE_USE_ENV_PROXY=1`.
- Тестовый аккаунт на боевом сайте. Его создаёт `prod-e2e-signup.mjs` (адрес-симулятор `delivered+…@resend.dev`, письмо
  читается через API Resend) и сохраняет вход в `/home/user/.secrets/qa-state.json`. Второй аккаунт для проверки изоляции —
  `prod-e2e-signup2.mjs` (`qa2-state.json`).
- Для `prod-db.mjs` (только чтение, SQL по HTTPS) — файл `/home/user/.secrets/neon-uris.json` со строками подключения Neon.

## Скрипты (`prod-checks/`)

| Скрипт | Что проверяет |
|---|---|
| `prod-e2e-signup.mjs`, `prod-e2e-signup2.mjs` | регистрация с настоящим письмом подтверждения |
| `prod-e2e-claimsignup.mjs`, `prod-e2e-claimconfirm.mjs` | путь нового посетителя: поиск → Claim с регистрацией → письмо → радар |
| `prod-e2e-claim.mjs` | привязка компании из-под существующего аккаунта |
| `prod-e2e-check.mjs`, `prod-export.mjs` | настоящая проверка тендерного пакета и выгрузки (id заявки — аргументом) |
| `prod-isolation.mjs <id заявки>` | чужое пространство и посетитель без входа не видят заявку, файлы и выгрузки |
| `prod-ui-checks.mjs` | правила интерфейса владельца: высоты, выравнивание, указатель, текущий пункт, копирование ID (28 проверок) |
| `prod-axe.mjs [id заявки] [публичные] [со входом]` | доступность (axe) на телефоне и десктопе |
| `prod-overflow-sweep.mjs <публичные> [со входом]`, `prod-overflow.mjs <путь> [auth] [ширина]` | горизонтальная прокрутка на 360 / 390 px и какой элемент её даёт |
| `prod-scroll.mjs` | `/pricing` открывается с верха из любого места; ссылки на разделы встают под шапку |
| `prod-look.mjs <имя> <auth\\|anon> <ширина> <пути>` | снимки страниц и сводный лист для просмотра глазами |
| `prod-cursor.mjs`, `prod-settings-nav.mjs`, `prod-404.mjs`, `prod-upload-diag.mjs`, `prod-shots.mjs`, `prod-signup.mjs` | точечные проверки по репортам |
| `prod-db.mjs "<select …>"` | чтение боевой базы (журнал ошибок, очередь задач, загрузка данных) |
| `convert-handoff.mjs`, `render-handoff.mjs` | разбор и отрисовка макетов из `docs/design/handoff/` |

## Инструменты (`tools/`)

| Файл | Назначение |
|---|---|
| `merge-verify.sh <ветка> <файл сообщения>` | слияние → проверка типов → линтер → тесты → сборка и браузерные сценарии → коммит → push → выкладка; останавливается на первой ошибке |
| `merge-continue.sh <файл сообщения>` | то же после ручного разбора конфликтов (`SKIP_UNIT=1` — не повторять уже прошедшие тесты) |
| `e2e-others.sh [каталог] [наборы]` | модульные браузерные наборы: `procurement bids notifications outreach` |
| `resolve.py <файл> <ours\\|theirs\\|both>` | разбор конфликтных блоков по правилу |
| `deploy.sh`, `deploy-staging.sh` | выкладка `origin/main` на Vercel (боевой сайт / стенд) из чистой копии |

Пути внутри скриптов (`/home/user/project-x`, `/home/user/deploy`, локальный Postgres `app/app`) — от облачной среды; на
другой машине их нужно поправить.
